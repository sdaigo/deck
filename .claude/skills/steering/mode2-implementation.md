# モード2: 実装

## 目的

tasklist.md に従って実装を進め、**進捗を確実にドキュメントに記録** します。

## 心構え: なぜ tasklist.md が重要か

tasklist.md はユーザーが進捗を確認する唯一の永続ドキュメントです。
tasklist.md を更新しないと、ユーザーは作業がどこまで進んだか把握できず、中断時の再開コストが増大します。
この前提を理解した上で、以下のルールに従ってください。

## MUST（必須）

- tasklist.md を常に開いた状態で実装
  - tasklist.md を見ないと計画との乖離に気付けず、不要な実装や重要な抜け漏れが発生するため
- タスク開始時に必ず Edit ツールで `[ ]` -> `[x]` に更新
  - リアルタイム更新がないと、中断時にどこまで進んだか不明になり再開コストが増大するため
- タスク完了時に必ず Edit ツールで完了を記録
  - 未記録のまま品質ゲートに進むと、レビュー範囲の特定が困難になるため
- **tasklist.md の全タスクが完了するまで作業を継続する**
  - 未完了タスクは「暗黙の負債」を生み、明示的な完了/スキップ判断がないとスコープが曖昧になるため
- タスク完全完了の原則（スキップ条件・分割方法）は **tasklist.md 冒頭** を参照

## NEVER（禁止）

- tasklist.md を見ずに実装を進める
  - 計画と実装の乖離は品質ゲートで予期しない問題を引き起こすため
- 複数タスクをまとめて更新する
  - バッチ更新は「どの時点で何が完了したか」のトレーサビリティを失わせるため
- **「時間の都合により」「別タスクとして実施予定」などの理由でタスクをスキップする**
  - 「後でやる」は実質「やらない」と同義であり、技術的に不要でない限り今やるべきため
- **未完了タスク（`[ ]`）を残したまま作業を終了する**
  - 未完了タスクは品質ゲートの前提条件を満たさず、レビューの信頼性を損なうため

## 実装フロー

### ステップ0: ブランチ確認

実装開始前に、現在のブランチが作業用ブランチであることを確認する:

```bash
git branch --show-current
```

- 作業用ブランチ（`feature/` または `hotfix/`）にいること
- `main`、`develop` にいる場合は実装を開始しない

誤ったブランチにいる場合は、ユーザーに報告してブランチを切り替える。

### ステップ1: tasklist.md を読み込む

```text
Read('.steering/[日付]-feature-[機能名]/tasklist.md')
```

全体のタスク構造を把握し、次に着手すべきタスクを特定する。

### ステップ2: タスクループ（各タスクで繰り返す）

#### 2-1. 次のタスクを確認

```text
tasklist.md を読み、次の未完了タスク（`[ ]`）を特定
```

#### 2-2. タスク開始を tasklist.md に記録（必須）

```text
Edit ツールを使って、tasklist.md の該当行を `[ ]` -> `[x]` に更新

例:
old_string: "- [ ] StorageService を実装"
new_string: "- [x] StorageService を実装"
```

**重要**: Edit ツールを実行した直後に、更新が成功したことを確認する。

#### 2-3. TDD: テストを先に書く（新規コードを含むタスクの場合）

タスクが新しい関数・サービス・コンポーネントの実装を含む場合、tdd-practitioner エージェントを起動してテストファーストで開発する:

```text
Task(general-purpose):
  "まず .claude/agents/tdd-practitioner.md を読み込み、TDD ワークフローに従ってください。
   対象タスク: [タスク内容]
   対象ファイル: [実装先パス]
   1. 失敗するテストを書く (RED)
   2. テストを通す最小限の実装を書く (GREEN)
   3. リファクタリング (REFACTOR)
   テスト完了後、カバレッジが80%以上であることを確認"
```

**適用条件**（以下のいずれかに該当するタスク）:

- 新規ファイルの作成（関数・クラス・フック・コンポーネント）
- 既存ファイルへの新規関数・メソッドの追加
- 新規 API エンドポイントの実装
- ビジネスロジックの変更（既存関数の振る舞いを変える修正）

**適用しない**（以下のすべてに該当するタスク）:

- 設定ファイルの変更のみ
- ドキュメント・コメントのみの変更
- リネーム・移動・フォーマット等の機械的リファクタリング
- 既存テストの修正のみ

#### 2-4. 実装を実行

```text
開発ガイドライン（docs/development-guidelines.md）に従って実装
2-3 で TDD を適用した場合は、テストを通す実装（GREEN）が完了した状態から続行
```

#### 2-4a. component-builder 起動（コンポーネント新規作成時のみ）

タスクが **コンポーネントの新規作成** を含む場合、component-builder スキルを起動する:

```text
Skill('component-builder')
  対象: [コンポーネント名]
```

**起動条件**:
- 新規の React コンポーネントファイルを作成するタスク

**起動しない**:
- 既存コンポーネントの修正のみ
- スタイリングのみの変更

#### 2-5. タスク完了を tasklist.md に記録（必須）

```text
実装完了後、必ず Edit ツールで tasklist.md を更新して完了を記録
サブタスクがある場合はサブタスクも個別に更新する
```

#### 2-6. 次のタスクへ

```text
ステップ2-1 に戻る
```

### ステップ3: フェーズ完了時の確認

各フェーズが完了したら:

1. **tasklist.md を読み込んで進捗確認**

   ```text
   Read('.steering/[日付]-feature-[機能名]/tasklist.md')
   ```

2. **完了したタスクを確認**
   - すべてのタスクが `[x]` になっているか
   - 見落としたタスクがないか

3. **test-runner でローカルチェック**

   品質ゲート前の早期検出として、フェーズ完了時に test-runner を起動する:

   ```text
   Task(general-purpose):
     "まず .claude/agents/test-runner.md を読み込み、ワークフローに従ってください。
      変更されたファイルに関連するテストを実行し、結果を報告してください。
      失敗がある場合は原因分析と修正案を提示してください。"
   ```

   - 失敗がある場合: 修正してからユーザーに報告
   - 全パスの場合: そのままユーザーに報告

4. **ユーザーに報告**

   ```text
   「フェーズN が完了しました。テスト結果: [Pass/Fail サマリ]。tasklist.md の進捗を確認してください。」
   ```

### ステップ3.5: 全タスク完了チェック（必須）

**全フェーズの実装完了後、モード2.5 に進む前に必ず実行**:

1. tasklist.md を読み込む
2. 未完了タスク（`[ ]`）がないか確認
3. 未完了タスクが見つかった場合:
   - **パターンA**: ステップ2 に戻り実装する
   - **パターンB**: タスクを分割してサブタスクを追加
   - **パターンC**: 技術的理由でのみスキップ（理由を明記）
4. 全タスク `[x]` を確認してからモード2.5 へ

## トラブルシューティング

### tasklist.md の更新を忘れた場合

1. **即座に更新を実行**

   ```text
   Read('.steering/[日付]-feature-[機能名]/tasklist.md')
   完了したタスクを特定し、すべて Edit ツールで [x] に更新
   ```

2. **ユーザーに報告**

   ```text
   「tasklist.md の更新が遅れていたため、現在の進捗を反映しました。」
   ```

### tasklist.md と実装の乖離

計画と実装が大きく異なる場合:

1. tasklist.md に注釈を追加: `- [x] タスク名（実装方法を変更: 理由）`
2. 必要に応じて新しいタスクを追加
3. Tier L の場合は design.md も更新

### Tier アップグレード

実装中に作業規模が当初の Tier を超えたと判断した場合、Tier アップグレードを検討する。

#### 検知トリガー

以下のいずれかに該当したら、Tier アップグレードを検討する:

| 現在の Tier | アップグレード条件 |
|:------------|:-------------------|
| **S -> M** | 変更ファイル数が 4 以上になった / 新規ファイル作成が必要になった / 新規テスト追加が必要になった |
| **S -> L** | アーキテクチャへの影響が判明した / 複数機能への影響が判明した |
| **M -> L** | 変更ファイル数が 10 を超えた / アーキテクチャへの影響が判明した / 新しい依存ライブラリが必要になった / 複数機能への影響が判明した |

#### アップグレード手順

1. **ユーザーに状況を報告し、アップグレードを提案する**

   ```text
   「実装中に当初の想定を超える変更が必要になりました。
    現在の Tier: [S/M]
    アップグレード理由:
    - [具体的な理由を箇条書き]

    Tier [M/L] にアップグレードしてステアリングファイルを作成しますか？
    A. アップグレードする（モード1 に戻ってステアリングファイル作成）
    B. 現在の Tier のまま続行する（ユーザー判断で許容）」
   ```

2. **ユーザーが A を選択した場合**
   - 現在の tasklist.md の進捗を保存（完了済みタスクはそのまま維持）
   - モード1 に戻り、Tier に応じたファイルを作成
   - 承認後、モード2 に戻って未完了タスクから再開

3. **ユーザーが B を選択した場合**
   - 現在の Tier のまま実装を継続
   - tasklist.md に注釈を追加

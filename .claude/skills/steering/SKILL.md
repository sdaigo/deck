# Steering スキル

Spec-Driven Development に基づき、作業の計画・実装・検証の全フローを制御するスキルです。
エージェントの並列起動によるコードベース調査、レビューチーム制による多角的な品質チェックを統合しています。

## スキルの目的

- **Tier 判定**: 作業規模を自動判定し、適切なフローを選択
- **ステアリングファイル管理**: requirements.md, design.md, tasklist.md の作成・進捗管理
- **品質ゲート**: レビューチーム制による多角的なコード品質チェック
- **フィードバックループ**: 実装結果の docs/ への自動反映提案

## 使用タイミング

ユーザーから作業指示を受けたら、このスキルを実行してください。
モード0（Tier 判定）から開始し、Tier に応じて後続モードが自動選択されます。

| モード | 名前 | タイミング | 詳細ファイル |
|:-------|:-----|:-----------|:-------------|
| **モード0** | Tier 判定 + 事前調査 | 作業指示受信時 | このファイル |
| **モード1** | ステアリングファイル作成 | Tier M/L 確定後 | `mode1-steering.md` |
| **モード2** | 実装 | ステアリングファイル承認後（または Tier S 判定後） | `mode2-implementation.md` |
| **モード2.5** | 品質ゲート | 全タスク完了後 | `mode25-quality-gate.md` |
| **モード3** | 振り返り + フィードバック | 品質ゲート通過後 | `mode3-retrospective.md` |

**各モードに進む際は、該当する詳細ファイルを Read ツールで読み込んでから実行すること。**

※ 品質ゲート（モード2.5）で Critical が解消しない場合、モード1 への差し戻しが発生することがある（詳細は `mode25-quality-gate.md` 参照）

## モード0: Tier 判定 + 事前調査

### 目的

ユーザーの作業指示を分析し、適切な Tier（S/M/L）を判定します。

### 手順

#### ステップ1: 並列エージェントで事前調査

以下の2エージェントを **並列** で起動する:

```text
Task(Explore):
  "ユーザーの作業指示: [指示内容]
   この作業で変更が必要なファイルを調査してください。
   報告内容:
   - 変更が必要なファイル一覧（パス付き）
   - 新規作成が必要なファイル
   - アーキテクチャ（docs/architecture.md）への影響の有無
   - 既存の類似実装パターンの有無"

Task(Plan):
  "ユーザーの作業指示: [指示内容]
   実装アプローチを概算設計してください。
   報告内容:
   - 推定変更ファイル数
   - 推定新規ファイル数
   - テスト追加の要否と規模
   - 主要な技術的リスク"
```

#### ステップ2: Tier 判定

エージェントの結果を統合し、以下の基準で判定する。
**最も高い Tier に該当する条件** で判定:

| 基準 | S | M | L |
|:-----|:--|:--|:--|
| 推定変更ファイル数 | 1-3 | 4-10 | 10+ |
| 新規ファイル作成 | なし | あり得る | 複数 |
| アーキテクチャへの影響 | なし | 軽微 | あり |
| テスト追加 | 既存テスト修正のみ | 新規テスト追加 | テスト設計が必要 |
| 新しい依存ライブラリ | なし | なし | あり |
| 複数機能への影響 | なし | なし | あり |

#### ステップ3: ユーザーに提示して確認

```text
「この作業は Tier [S/M/L] と判断しました。
 根拠: [判定理由を箇条書き]
 [Tier に応じたフロー説明]
 よろしいですか？」
```

#### ステップ4: ブランチ作成

Tier 承認後、実装（またはステアリングファイル作成）に入る前に作業用ブランチを作成する。
ブランチ命名規則は `.claude/rules/common/git-workflow.md` に従う。

```bash
git checkout develop
git pull origin develop
git checkout -b feature/[機能名]
```

> **緊急修正（hotfix）** は別スキルで対応する。`hotfix/` ブランチの作成・運用は hotfix スキルを参照のこと。

**例外**: ドキュメントのみの変更（コード変更なし）の場合、現在のブランチでの作業を許可する（ユーザー判断）。

#### ステップ5: Tier に応じた分岐

- **Tier S**: 簡易 tasklist を作成してからモード2（実装）へ進む（モード1 はスキップ）
  - planner エージェントにフラットなチェックリストを作成させる
  ```text
  Task(general-purpose):
    "まず .claude/agents/planner.md を読み込んでください。
     以下の作業計画をフラットなチェックリスト形式で作成してください。

     作業内容: [ユーザーの作業指示]
     対象ファイル: [Explore の調査結果]

     フォーマット:
     - フェーズ分けなし、フラットなチェックリスト
     - 各タスクは具体的で実装可能な粒度
     - テスト追加が必要ならタスクに含める
     - テンプレート: .claude/skills/hotfix/templates/tasklist.md
     - 出力先: .steering/[YYYYMMDD]-feature-[機能名]/tasklist.md"
  ```
  - 作成後、ユーザーに確認してからモード2 へ
- **Tier M**: モード1（ステアリングファイル作成）へ。requirements.md + tasklist.md を作成
- **Tier L**: モード1（ステアリングファイル作成）へ。requirements.md + design.md + tasklist.md を作成

## 重要なリマインダー

**このスキルの最も重要な役割は2つ:**

1. **tasklist.md の進捗管理を確実に行うこと**
   - tasklist.md はユーザーが進捗を確認する唯一の永続ドキュメント
   - タスク開始・完了時に必ず Edit ツールで更新する

2. **レビューチームによる多角的な品質チェック**
   - 1体のレビュアーに全観点を任せない
   - 観点別に並列起動して深いレビューを実現

実装中は常に「ユーザーが tasklist.md を見たときに進捗が分かるか？」を自問してください。
